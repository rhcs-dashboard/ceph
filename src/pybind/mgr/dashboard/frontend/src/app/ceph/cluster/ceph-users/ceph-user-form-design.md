# Ceph user form

Create, edit, and import for Administration → Ceph users are Angular forms. They no longer render the free-text fields generated by the backend CRUD schema.

## Problem

The old Create User page used free-text fields for the user entity, the capability entity, and the capability string. The page marked `test.1` as valid. Create then failed in the cluster:

```text
Error EINVAL: bad entity name
```

Ceph entity names are `type.id`. `test.1` has no known type. The name that succeeds is `client.test.1`. Capability entities (`mon`, `mgr`, `osd`, `mds`) and strings such as `allow r` were also typed by hand, so a typo was easy.

## Does this block use of the product?

Yes. An administrator cannot finish creating a Ceph user from the dashboard unless they already know the CephX `type.id` format. The form accepts `test.1`, the cluster rejects it, and the error does not say that the name must look like `client.test.1`. That stops the create workflow.

Editing and deleting users that already exist still works from the Ceph users list. Import works only when the keyring already contains a valid entity name. The failure is limited to creating a user with a name the form did not check.

## Create and edit

```text
Entity type *     [ client v ]     client, osd, mon, mgr, mds
Entity name *     [ test.1     ]
User entity       client.test.1    read-only, this value is submitted

Capabilities
  Entity *                 [ mon v ]     mon, mgr, osd, mds
  Entity capabilities *    [ allow r v ] allow r, allow rw, allow rwx, allow *
                                         plus the profiles documented for that daemon
```

`test.1` is the entity name. It is not submitted on its own. With type `client`, the user entity is `client.test.1`. Pasting `client.test.1` into the name fills the type and leaves `test.1` in the name.

The name is rejected, and Create stays on the page, when the composed entity is not `type.id`. The field error is:

```text
User entity must include a valid Ceph entity prefix, for example client.test.1
```

Empty name uses "This field is required." A name that is already in the cluster uses "This user entity already exists. Edit that user to change capabilities."

Edit keeps the type and name read-only. Saving replaces every capability on that user. A capability string that is not in the list stays selected so an edit does not drop it.

## Capabilities

| Daemon | Access options | Profiles |
| --- | --- | --- |
| mon | allow r, allow rw, allow rwx, allow * | osd, mds, rgw, rbd, rbd-mirror, bootstrap-osd, bootstrap-mds, bootstrap-rbd, bootstrap-rbd-mirror, simple-rados-client, simple-rados-client-with-blocklist, fs-client, role-definer, crash |
| mgr | allow r, allow rw, allow rwx, allow * | rgw, rbd, rbd-read-only, crash |
| osd | allow r, allow rw, allow rwx, allow * | rgw, rbd, rbd-read-only |
| mds | allow r, allow rw, allow rwx, allow * | none |

Each daemon can be added once. An OSD `allow r`, `allow rw`, `allow rwx`, or `allow *` warns that the user can access every pool. `profile role-definer` warns that it grants full control of the auth subsystem.

Reference: [Authorization (Capabilities)](https://docs.ceph.com/en/reef/rados/operations/user-management/#authorization-capabilities).

## API

The list, delete, and export actions stay on the Ceph users table.

| Action | Request |
| --- | --- |
| Create | `POST /api/cluster/user` with `user_entity` and `capabilities` |
| Edit | `PUT /api/cluster/user` with the same body |
| Import | `POST /api/cluster/user` with `import_data` |

`user_entity` is always the composed name, for example `client.test.1`. `capabilities` is `[{ "entity": "mon", "cap": "allow r" }]`.
